# Architecture baseline

```text
React UI (Chat / Orb / Settings / Diagnostics)
        │ typed Tauri IPC + events
        ▼
Rust Application Core
  ├─ Lifecycle / State / Event Bus
  ├─ Module Manager
  ├─ AI Engine
  ├─ Voice Engine
  ├─ Memory Engine
  ├─ Telegram Engine
  ├─ Windows/System Tools
  ├─ Settings / Diagnostics / Security
  └─ Storage (SQLite)
```

## Module lifecycle
Каждый optional module имеет stable ID, metadata, dependencies/capabilities, `initialize`, `start`, `stop`, `status`, `health_check`, структурированные ошибки. Отключение останавливает фоновые задачи и освобождает ресурсы. Циклы зависимостей запрещены.

## Module Manager
Решения — ADR-011 (core-сервисы и compile-time модули), ADR-012 (двухфазные изменения), ADR-014 (жизненный цикл и политика сбоев) и ADR-015 (конфигурация, настройки и автозапуск). Код — `src-tauri/src/modules/`.

- **ID модуля:** `domain.name` — строчные латинские буквы, цифры и `_`, не меньше двух непустых сегментов (`ai.lmstudio`, `voice.stt`).
- **Граф зависимостей** (`graph.rs`) проверяется при сборке каталога: повторяющиеся ID, неизвестные зависимости, зависимость от самого себя, циклы (ошибка содержит путь цикла). Порядок запуска — топологический, при равенстве по ID; порядок остановки — строго обратный.
- **Статус** = `enabled` (решение пользователя: `Some(true)`, `Some(false)` или `None` — неизвестно) + `state` (факт):

```text
Stopped ─start─▶ Initializing ─▶ Starting ─▶ Running ─stop─▶ Stopping ─▶ Stopped
Initializing / Starting ── ошибка · паника · таймаут · выход ──▶ Failed{Initialize | Start}
Running ── фоновая задача: ошибка или паника ──▶ Failed{Run}           ┐
Running ── паника проверки health ──▶ Failed{HealthCheck}             ├─ затем каскад зависимым
Running (зависимый) ── зависимость упала ──▶ Stopping ──▶ Blocked{by, DependencyFailed}
Stopping ── ошибка · паника · таймаут · прерванные задачи · сбой удаления ──▶ Failed{Stop}
выход: очередь модуля не дошла к сроку ──▶ Failed{Stop}                (без вызова stop)
загрузка: запись или значения по умолчанию ──▶ {Some(e), Stopped}
загрузка: ошибка чтения ──▶ {None, ConfigUnavailable}                  (в сеансе выхода нет)
автозапуск: зависимость выключена · недоступна · упала
            ──▶ Blocked{by, DependencyDisabled | DependencyConfigUnavailable | DependencyFailed}
автозапуск: некорректные настройки включённого модуля ──▶ Failed{Settings}
ConfigUnavailable ── enable · disable · recover · restart · update_settings ──✗
Failed / Blocked ── только подтверждённый recover ──▶ Initializing …    (автоматических переходов нет)
```

`enabled` меняет только пользователь: `enable`, `disable` и шаги включения в подтверждённом плане. Сбои, блокировка и выход его не меняют. В `Initializing`, `Starting`, `Running`, `Stopping` и `Blocked` модуль всегда включён (`Some(true)`, решение 23); `ConfigUnavailable` — всегда `None`; `None` бывает только с `ConfigUnavailable` или со `Stopped` до готовности менеджера.

- **Планы** (`plan.rs`) строятся без побочных эффектов:

| Действие | Применимо к | Затронутые | Подтверждение |
|---|---|---|---|
| `enable` | `enabled = Some(false), state = Stopped` | выключенные транзитивные зависимости (будут включены и запущены) | если затронутые есть |
| `disable` | `enabled = Some(true)` | включённые транзитивно зависимые (будут отключены; остановка в обратном порядке) | если затронутые есть |
| `recover` | `Failed`, `Blocked` | недостающие зависимости цели и заблокированные зависимые, которых план восстанавливает | **всегда** |
| `restart` | `Running` | работающие транзитивно зависимые (остановка в обратном порядке, затем запуск) | если затронутые есть |

Зависимость в `Failed`, `Blocked`, `ConfigUnavailable` или в переходном состоянии делает план неприменимым (`blockers`). К модулю с неизвестным решением (`None`) не применимо ни одно действие, а каскады `disable` и `restart` его пропускают. `apply` выполняет только план, одобренный `verify`; результаты: `Applied`, `ConfirmationRequired`, `ImpactChanged`, `NotApplicable`. Перед выполнением решения плана (`Enable` / `Disable`) записываются в хранилище одним пакетом; ошибка записи (`Store`) или некорректные настройки запускаемого модуля (`InvalidSettings`) — ничего не меняется.
- Изменения статусов публикуются только через центральную шину событий (раздел «Event Bus»).

### Менеджер жизненного цикла (#9, ADR-014)
- **Actor:** одна задача владеет реестром и выполняет команды по очереди. Это единственный компонент, меняющий статусы. Изменение сначала попадает в снимок, затем публикуется как `StatusChanged`.
- **Handle** (`ModuleManagerHandle` в `AppState`):
  - `modules()`, `module()`, `statuses()`, `plan()` и `get_settings()` читают снимок, не дожидаясь менеджера; до готовности — `NotReady` (`is_ready()` — только для тестов);
  - `apply`, `check_health`, `update_settings` и `shutdown` отправляют команду по `mpsc` и получают ответ по `oneshot`.
- **Экземпляры:** новый при каждом запуске; каждый вызов модуля — в отдельной задаче с таймаутом. Удаляется экземпляр тоже вне задачи менеджера — на пуле блокирующих потоков, с ограниченным ожиданием: паника или зависание `Drop` не останавливают менеджер (ADR-014). Фоновые задачи модуль запускает через `ModuleContext::spawn`; менеджер отменяет их при остановке и прерывает те, что не завершились.
- **Порядок освобождения:**
  - остановка: отмена токена → `stop` → удаление экземпляра (в остатке срока `stop`) → ожидание фоновых задач → прерывание оставшихся;
  - ошибка `initialize` / `start`: `Failed { phase }` → отмена токена → удаление → ожидание задач (решение 7); зависший `Drop` не задерживает `Failed`;
  - паника или срок удаления после успешного `stop` → `Failed { Stop }` с прежними текстами; причину различает журнал (`call = "drop"`).
- **Сбои** не перезапускают ничего сами. Упавший модуль получает `Failed`, его работающие зависимые останавливаются в обратном порядке и получают `Blocked`. Вернуть их может только подтверждённый `recover`. После запроса выхода сбой фоновой задачи только пишется в журнал (`warn` или `debug`, с текстом): статус и зависимые не меняются, итог даёт остановка в `shutdown_all`. Исключение при выходе (ADR-015): если обработка сбоя уже шла, идущая остановка доводится до конца, а следующая остановка зависимого не начинается — остальных зависимых останавливает `shutdown_all`.
- **Health** — только по запросу, информационно; событие `HealthChanged` публикуется при изменении значения.
- **Ресурсы:** экземпляр владеет всем, что выделил. При ошибке `initialize` / `start` модуль сам освобождает выделенное, а удаление экземпляра не оставляет ресурсов (ADR-014).
- **Ограничение таймаутов:** асинхронный таймаут прерывает вызов только там, где тот уступает управление. Блокирующий нативный код так прервать нельзя, поэтому модуль выносит его в отдельный поток (например, `spawn_blocking`).
- **Некорректный каталог:** ошибка пишется в лог на уровне `error` с причиной, приложение запускается без модулей.

### Настройки и автозапуск (#10, ADR-015)
- **Конфигурация модуля** — решение пользователя (`enabled`) и собственные настройки (объект JSON). Хранилище — трейт `ModuleConfigStore` (`load`, атомарный `save_batch`); сейчас `InMemoryConfigStore`. **Настройки и признак `enabled` пока не сохраняются между перезапусками приложения** — сохранение в SQLite появится в MM-5B (#21).
- **При старте** менеджер читает конфигурацию всех модулей (нет записи → `default_enabled` и `default_settings()`), затем запускает включённые модули в топологическом порядке, затем становится готовым (`ready`, событие `ManagerReady`). Выключенная, недоступная или упавшая зависимость → `Blocked` с первопричиной; неявных включений и повторов нет. `Failed` и `Blocked` — состояния только текущего запуска и не сохраняются; при следующем запуске включённые модули стартуют обычным порядком. Это не считается автоматическим восстановлением.
- **Готовность:** `ready = true` — первоначальная загрузка завершена и снимок достоверен; это не гарантия, что менеджер ещё принимает команды. До готовности чтение возвращает `NotReady`, команды ждут в очереди. Выход во время автозапуска: прерванный модуль получает `Failed { phase }` (ADR-014), затем `ManagerReady`, затем остановки `shutdown_all`. Выход во время загрузки: `ready` остаётся `false`, `ManagerReady` нет.
- **Недоступная конфигурация:** ошибка чтения записи → `{ None, ConfigUnavailable }`; модуль не запускается, значения по умолчанию не подставляются, запись не перезаписывается, зависимые → `Blocked { by, DependencyConfigUnavailable }`. Внутри сеанса выхода нет; при следующем запуске запись читается снова. Восстановление — MM-5B.
- **Настройки** проверяются фабрикой модуля (`validate_settings`) после общих проверок: корень — объект, ≤ 65 536 байт компактного JSON, глубина ≤ 128, без ключей, похожих на секреты. Экземпляр получает их через `ModuleContext::settings()` с `initialize`. `update_settings` сохраняет новое значение и публикует `SettingsChanged`; работающий модуль получает пометку `restart_required` и **не** перезапускается сам — применить настройки можно подтверждённым `restart`. Некорректные настройки включённого модуля при старте → `Failed { Settings }`, у выключенного — только запись в журнал.
- Методы фабрики (`create`, `default_settings`, `validate_settings`) изолированы от паник.

## Event Bus
Решение — ADR-013. Код — `src-tauri/src/events/`.

- Одна шина на приложение (`EventBus` в `AppState`) — **единственный механизм межмодульных уведомлений**. Она только доставляет уведомления: без запросов и команд, без влияния на статусы и жизненный цикл модулей, без фоновых задач.
- Событие — `EventEnvelope { seq, at_unix_ms, source, event }`. `event` — `AppEvent` по доменам; сейчас это `Module(StatusChanged { id, previous, current })`, `Module(HealthChanged { id, health })` (#9), `Module(SettingsChanged { id, restart_required })` без значений настроек и `Module(ManagerReady)` (#10). `source` проставляет ядро: `publish` не принимает источник.

| Ситуация | Поведение |
|---|---|
| Нет подписчиков | `publish` успешен, событие никому не доставляется, `seq` растёт |
| Одновременная публикация | `seq` уникальны; все подписчики получают события в порядке `seq` |
| Поздний подписчик | получает только события после подписки; текущее состояние — из снимка (#9) |
| Переполнение: отставание больше `capacity` (по умолчанию 256) | `publish` не ждёт; отставший получает `Lagged { missed }`, затем самое старое сохранённое событие, и пересинхронизируется по снимку |
| Закрытие: `close()` на выходе или удаление всех handle | подписчики дочитывают опубликованное, затем `Closed`; `publish` → `BusClosed` |
| `close` или `subscribe` во время публикации | ждут, пока публикация завершится; новый подписчик получает события только после неё |

- **Требование к использованию API:** waker задачи, ожидающей `Subscriber::recv`, не должен синхронно вызывать шину (`publish`, `subscribe`, `close`) — подписчики пробуждаются под блокировкой шины, иначе взаимоблокировка.
- **Разграничение механизмов** (решение 26, реализовано в #9): `mpsc` — команды менеджеру; `oneshot` — результат команды; `watch` — только чтение снимка статусов, без `changed()`; Event Bus — единственный механизм уведомления об изменениях.

## IPC и мост событий (#11)
Код — `src-tauri/src/dto/`, `src-tauri/src/commands/`, `src-tauri/src/events/ui_bridge.rs`, `src/types/modules.ts`, `src/lib/ipc.ts`.

- **Команды** — тонкий слой: разбор аргументов, вызов handle менеджера, преобразование в DTO. Планы, проверка подтверждений и настроек остаются в менеджере. Команды: `list_modules`, `get_module`, `plan_module_change`, `apply_module_change`, `check_module_health`, `get_module_settings`, `update_module_settings`. `replace_config` — MM-5B (#21).
- **DTO** сериализуются в camelCase; `src/types/modules.ts` — их зеркало, написанное вручную. Тест сериализации падает, если ключа или тега из Rust нет в TypeScript.
  - `enabled: boolean | null` (`null` — конфигурация не прочитана); состояние — объект с полем `kind`, включая `configUnavailable`; причина блокировки — включая `dependencyConfigUnavailable`; фаза сбоя — включая `settings`.
  - `health` в `ModuleDto` — последний результат проверки работающего экземпляра из снимка менеджера (`null`, пока проверки не было); только для показа.
- **Ожидаемые исходы — не ошибки.** `apply_module_change` возвращает `ApplyResultDto`: `applied { report }`, `confirmationRequired { plan }`, `impactChanged { plan }`, `notApplicable { blockers }`. Подтверждение проверяет менеджер по плану на момент применения, а не UI; `recover` всегда требует `confirmed = true`.
- **`ErrorDto { code, message }`** — только для настоящих ошибок. `code` стабилен: `invalid_id`, `unknown_module`, `action_not_applicable`, `invalid_settings`, `not_running`, `not_ready`, `shut_down`, `config_unavailable`, `store`, `internal`. `message` — фиксированный безопасный текст: без текста исходной ошибки, путей и значений настроек (подробности — только в журнале). Единственная переменная часть — причина в `invalid_settings`, которая по ADR-015 называет проблему, но не значение.
- **Мост событий** — фоновая задача ядра: подписывается на шину до запуска менеджера и пересылает события модулей в webview как `modules://event` (`{ seq, atUnixMs, event }`; `event.type` — `statusChanged`, `healthChanged`, `settingsChanged`, `managerReady`). При отставании (`Lagged`) отправляет `modules://resync { missed }` — UI загружает список заново. Закрытие шины завершает задачу. Мост только доставляет: статусы не меняет и действий не запускает.
- **Готовность для UI** — на контрактах MM-5A, без нового события: `src/lib/ipc.ts` сначала подписывается на события, затем вызывает `list_modules`; при ответе `not_ready` ждёт `managerReady` и повторяет вызов. До этого у UI нет списка — он показывает инициализацию и не считает отсутствие данных пустым списком.
- **Фронтенд:** `invoke` и `listen` вызываются только в `src/lib/ipc.ts`.
- **Права webview** (`capabilities/default.json`) не менялись: `core:default` достаточно для команд приложения и `listen`.
- Команды пишут в журнал на уровне `debug` только имя команды и код ошибки — без аргументов и значений.

## Завершение приложения
Решение пользователя от 2026-11-09 (решение 28 в #13), реализовано в #9 (ADR-014).

1. Остановить активные модули.
2. Дождаться завершения операций остановки и публикации соответствующих `StatusChanged`.
3. Вызвать `close_events()`.
4. Выполнить `flush_logs()`.
5. Завершить приложение.

Шина не должна закрываться до завершения остановки модулей, иначе последние события жизненного цикла могут потеряться. Ожидание в шагах 1–2 ограничено общим таймаутом (`SHUTDOWN_TIMEOUT`, 10 с).

- **Как устроено** (`src-tauri/src/lib.rs`):
  - первый `ExitRequested` откладывает выход и останавливает модули вне главного потока;
  - затем выход запрашивается снова и проходит — цикла нет;
  - на `RunEvent::Exit` вызываются `close_events()` и `flush_logs()`.
- **Когда срок истёк:**
  - модули, до которых не дошла очередь, завершаются принудительно без `stop` — токен отменяется, удаление экземпляра запускается и не ждётся, фоновые задачи прерываются;
  - они получают `Failed { phase: Stop }`, изменение публикуется, ошибка пишется в лог;
  - удаления, которые менеджер перестал ждать и которые к концу остановки ещё не завершились, перечисляются в логе до ответа; освобождение их ресурсов к ответу не гарантируется.
- **Сигнал выхода приоритетнее очереди** (ADR-015): менеджер ждёт команды под сигналом выхода; после запроса текущая операция завершается (прерванный запуск — `Failed { phase }`), если подготовка закончилась — публикуется `ManagerReady`, затем накопленные сообщения разбираются без выполнения (команды — `ShutDown`, отчёты — в журнал) и начинается `shutdown_all`. В режиме выхода статусы меняет только `shutdown_all`.
- **После остановки модулей** (ADR-014, вариант B) менеджер:
  1. разбирает очередь, не закрывая её: отчёты о сбоях — только в лог, команды получают `ShutDown`, повторные запросы выхода ждут;
  2. пишет `module manager stopped`;
  3. закрывает очередь и разбирает остаток;
  4. отпускает повторные запросы выхода (`ShutDown`);
  5. отвечает.

  Запрос после закрытия очереди сразу получает `ShutDown` — уже после строки о завершении, поэтому запасной путь выхода не сбрасывает лог раньше неё. После ответа менеджер ничего не пишет, не публикует и не принимает команд, поэтому после `close_events()` событий нет. Отчёт, который уже нельзя отправить менеджеру, пишет в лог супервизор задачи. Ограничение: отчёт, пришедший около момента закрытия очереди, пишется после `module manager stopped` (до ответа).

## AI
LM Studio — default provider. Используй provider adapter. Поддержи connection test, model discovery где доступно, streaming, cancellation, generation settings и structured tool calls. Tool call — запрос, а не разрешение: отдельная policy layer валидирует действие.

## Voice
Отдельные интерфейсы/адаптеры для audio devices, STT, TTS, VAD и wake-word. Возможности и совместимость движков должны отражаться в настройках.

## Memory
История и долговременная память — разные сущности. Пользователь может просматривать, редактировать и удалять долговременную память. Начать с SQLite и FTS5; vector search отложить до доказанной необходимости.

## Windows tools
Только типизированные allowlisted операции. Read-only и изменяющие состояние возможности разделены. Чувствительные/необратимые действия требуют подтверждения. Не давать модели универсальный execute command.

## Secrets
Windows Credential Manager / DPAPI-backed storage или поддерживаемый эквивалент. Секреты не попадают в SQLite plaintext, логи, crash reports или экспорт диагностики. В настройках модулей секреты запрещены — допустима только ссылка на хранилище ОС (`token_ref`); ключи, похожие на секреты, отклоняются проверкой (страховка, не гарантия), значения настроек не пишутся в журнал и события (ADR-015).
