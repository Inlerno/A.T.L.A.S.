## 2026-11-09 — Issue #9: MM-4 — жизненный цикл модулей, изоляция сбоев, выход

Менеджер жизненного цикла: `src-tauri/src/modules/{contract,context,manager}.rs`. Решение — ADR-014; описание — раздел «Module Manager» и «Завершение приложения» в `ARCHITECTURE.md`.

### Что сделано
- `contract.rs`:
  - трейты `Module` (`initialize` / `start` / `stop` / `health_check`) и `ModuleFactory`;
  - `Health`, `ModuleFailure`;
  - `ModuleStatus::is_consistent()` — проверка инварианта (решение 23).
- `context.rs`: `ModuleContext` — подписка на шину, токен отмены, фоновые задачи под надзором (`TaskTracker` + `CancellationToken`).
- `manager.rs`:
  - actor с командами по `mpsc` и ответами по `oneshot`, снимок статусов в `watch` (только чтение);
  - выполнение планов, изоляция вызовов, каскад `Blocked`, health по запросу;
  - выход с общим таймаутом, таймауты как именованные константы, тексты для пользователя.
- `events/types.rs`: событие `ModuleEvent::HealthChanged`.
- `app/state.rs`, `lib.rs`: менеджер создаётся в `setup` (модули не запускаются). Выход идёт в порядке решения 28: первый `ExitRequested` откладывает выход и останавливает модули, повторный проходит, затем на `Exit` вызываются `close_events()` и `flush_logs()`.
- Прочее: `clock.rs` (общий `unix_time_ms` для шины и менеджера), `ModuleGraph: Default` (пустой граф для некорректного каталога), `modules::catalog()` (пока пуст).
- CI: шаг, запрещающий `panic = "abort"` в `src-tauri/Cargo.toml`. Проверен локально: чистый файл — успех, `panic = "abort"` и `panic='abort'` — ошибка.

### Решения, которых нет в тексте #9 (приняты пользователем 2026-11-09 по ревью PR #20)
Записаны в ADR-014 («Принятые решения») и как решение 29 в #13. Нумерация совпадает с описанием PR.
1. **`async-trait` не добавлен**: используются ручные `Pin<Box<dyn Future + Send>>` — вариант, предусмотренный #9.
2. **`macros` не подключён** (решение 27): вместо `select!` используется `CancellationToken::run_until_cancelled`.
3. **`Module: Send + Sync`**: future от `health_check(&self)` должен быть `Send`.
4. **Проверка health без ответа держит экземпляр.** Экземпляр остаётся у проверки и не теряется, состояние не меняется. Новая проверка не запускается. Поздний ответ возвращает экземпляр, поздняя паника → `Failed { HealthCheck }` с каскадом. При остановке менеджер ждёт проверку в пределах таймаута `stop`; если ответа нет — модуль останавливается без вызова `stop` (`Failed { Stop }`).
5. **`HealthChanged`** публикуется только при изменении значения.
6. **`stop` не вызывается** после неудачных `initialize` / `start`: экземпляр не запускался. Его фоновые задачи отменяются и прерываются менеджером.
   - **Уточнение пользователя:** модуль сам освобождает частично выделенные ресурсы до возврата ошибки, а удаление экземпляра не должно оставлять ресурсов. Это записано в контракте `Module` (`contract.rs`) и в ADR-014.
7. **`Failed` выставляется сразу** при обнаружении сбоя, освобождение ресурсов идёт после. Для сбоев во время работы это порядок из #9; для остальных сбоев — тот же.
8. **Запрос выхода** прерывает идущие `initialize` / `start` / `health` сразу. Оставшиеся шаги плана пропускаются (`interrupted`). После запроса `apply` и `check_health` возвращают `ShutDown`.
9. **Двухфазный выход**: `ExitRequested` + `prevent_exit` + повторный `exit()`; запасной путь в `RunEvent::Exit`.
10. **Тексты для пользователя** написаны по-русски, как «проверка не ответила» в #9, и собраны в `manager::text`. Ошибка, которую вернул сам модуль, показывается как есть: контракт `ModuleFailure` требует, чтобы текст был безопасным для показа.
11. **Некорректный каталог**: приложение работает без модулей. Встроенный каталог проверяется тестом.
    - **Уточнение пользователя:** ошибка обязательно пишется в лог на уровне `error` вместе с причиной, молчаливого игнорирования нет. Это проверяет тест `an_invalid_catalog_is_logged_and_leaves_the_manager_without_modules`. Мутационная проверка: без записи в лог и с уровнем `warn` тест падает.
12. **Значения таймаутов** и их обоснование — в ADR-014.

Ограничение таймаутов записано явно — в контракте `Module`, в ADR-014 и в `ARCHITECTURE.md`. Асинхронный таймаут прерывает вызов только там, где тот уступает управление. Блокирующий нативный код так прервать нельзя, поэтому модуль выносит его в отдельный поток.

**Мутационная проверка.** 17 намеренных поломок менеджера и контекста, все 17 обнаружены. Среди них:
- снимок не обновляется;
- зависимые останавливаются в прямом порядке;
- нет каскада после сбоя;
- повторный запуск упавшего модуля;
- не ответившая проверка health теряет экземпляр;
- остановка не ограничена сроком выхода;
- модули не завершаются принудительно по сроку;
- менеджер работает после команды выхода;
- принимаются отчёты остановленного экземпляра;
- нет отмены после неудачного запуска;
- `disable` скрывает `Failed { Stop }`;
- нет прерывания `initialize` или плана при выходе;
- нет `abort` у задач;
- заблокированный модуль выключается (нарушение инварианта).

Две поломки сначала выжили: повторный запуск после неудачной остановки при `restart` и выполнение плана после запроса выхода. Для них добавлены тесты.

**Найдено при самопроверке и исправлено в коде.** При `restart` Tauri не позволяет отложить выход, и модули останавливает запасной путь в `RunEvent::Exit`. Фоновая остановка, закончив, запрашивала бы выход ещё раз. На уже завершающемся цикле событий Tauri обрабатывает такой запрос через `std::process::exit`, и процесс мог закончиться раньше сброса логов. Теперь у выхода есть фаза `Exiting`: после начала `Exit` фоновая остановка выход не запрашивает (тест `an_exit_that_could_not_wait_stops_the_modules_itself`).

**Найдено и исправлено в тестах.** Тест «детали паники — только в лог» иногда не видел записей лога при параллельном запуске. Причина — кеш интереса `tracing` к местам логирования. Он общий для процесса: пока зарегистрирован один подписчик, интерес нового места вычисляется по подписчику того потока, который первым до него дошёл. Параллельный тест без подписчика кешировал «не интересно», и подписчик теста, заданный для его потока (`set_default`), этих записей не получал. Теперь в бинаре unit-тестов один глобальный подписчик с буфером на поток.

**Стабильность** (облачный Linux): без сбоев прошли 100 прогонов тестов модулей, 50 прогонов всех unit-тестов, 30 — на одном ядре, 20 — в один поток.

## 2026-11-09 — Issue #8: MM-3 — центральная шина событий

Центральная типизированная шина уведомлений: `src-tauri/src/events/{mod,types,bus}.rs`. Решение — ADR-013 (включает решения 24 и 25 из #13); описание — раздел «Event Bus» в `ARCHITECTURE.md`.

### Что сделано
- `types.rs`: `EventEnvelope { seq, at_unix_ms, source, event }`, `EventSource::Core`, `AppEvent::Module(ModuleEvent::StatusChanged { id, previous, current })`.
- `bus.rs`:
  - `EventBus` — клонируемый handle: `new(capacity)`, `publish(event) -> Result<seq, BusClosed>`, `subscribe()`, `close()`;
  - `Subscriber::recv()` → `Received::Event` / `Lagged { missed }` / `Closed`.
- `AppState` хранит шину. На `RunEvent::Exit` шина закрывается (`close_events`), затем сбрасывается лог — строка `event bus closed` попадает в файл.

### Уточнения в рамках #8 (приняты пользователем 2026-11-09 по ревью PR #17)
Зафиксированы в ADR-013 и в решении 27 в #13.

- **`EventSource::Module(ModuleId)` не добавлен.** Его отправитель — публикация модулями, а она вне скоупа #8 (впервые в #12). Без отправителя вариант не создаётся нигде, и тестовая сборка не проходит `clippy -D warnings`. Обойти это можно только искусственным тестом или точечным `allow`. Поэтому вариант добавляется вместе с отправителем — по тому же правилу, что и варианты событий (решение 5 в #13). Поле `source` и правило «источник проставляет ядро» действуют уже сейчас.
- **Явное закрытие `close()`.** `App::run` завершает процесс через `std::process::exit`, поэтому handle шины в `AppState` никогда не удаляется. Без явного закрытия подписчики не получили бы `Closed`.
- **Ёмкость — только степень двойки до 4096.** `tokio` 1.54.1 округляет ёмкость вверх до степени двойки (так сказано в его документации). Поэтому другие значения отклоняются, а не округляются молча. Неверное значение — ошибка в коде и вызывает панику при создании. Для `DEFAULT_CAPACITY` корректность проверяется при компиляции, поэтому `setup` паниковать не может.
- **`macros` не подключён:** зависимости не добавляются только ради удобства тестов. Тесты запускают futures на `tokio::runtime::Builder::new_current_thread()` (feature `rt`), поэтому `tokio-macros` в `Cargo.lock` не появился.
- В однопоточных тестах сообщение уже должно ждать подписчика: тест опрашивает `recv` один раз и падает, а не зависает.

### Детерминированная проверка порядка (по ревью PR #17)
Первая версия проверяла одновременную публикацию только стресс-тестом и ловила нарушение порядка не в каждом запуске (27–29 из 30). По запросу пользователя добавлены тесты, которые воспроизводят нужное чередование потоков синхронизацией, а не ждут случайной гонки. Архитектура шины не менялась.
- **Точки перехвата** — модуль `test_hooks` в `bus.rs`, компилируется только в тестовой сборке (`#[cfg(test)]`); в приложении их нет. Хуки задаются для отдельного потока (`thread_local!`), поэтому параллельные тесты друг другу не мешают:
  - `BEFORE_SEND` — вызывается в `publish`, когда у события уже есть `seq`, но оно ещё не отправлено (блокировка шины удерживается). Тест останавливает в этой точке публикующий поток;
  - `BEFORE_WAIT` — вызывается, когда поток собирается ждать блокировку шины, занятую другим потоком. Так тест точно знает, что поток ждёт, и не угадывает это по времени.
- **Тесты:**
  - `overlapping_publications_are_delivered_in_seq_order` — A получил `seq` 1 и остановлен перед отправкой; B и C начинают публикацию и оба обязаны ждать; после продолжения A три подписчика получают события строго в порядке `seq`, и `seq` каждого события совпадает с числом, которое вернул его `publish`;
  - `close_waits_for_a_publication_in_progress` — `close` во время публикации ждёт её; событие доставляется до `Closed`;
  - `subscription_during_a_publication_starts_after_it` — `subscribe` во время публикации ждёт её; новый подписчик получает только следующие события.
- Стресс-тесты (8 потоков × 400 событий; закрытие при гонке) сохранены как дополнительная проверка случайных чередований.
- В документацию API (`bus.rs`, ADR-013, `ARCHITECTURE.md`) добавлено **требование к использованию**: waker задачи, ожидающей `recv`, не должен синхронно вызывать шину — подписчики пробуждаются под блокировкой шины.

## 2026-11-09 — Issue #7: MM-2 — статусы, граф зависимостей, планы изменений

Чистая логика без async и без runtime: `src-tauri/src/modules/{mod,contract,graph,plan}.rs`. Решения — ADR-011, ADR-012; описание — раздел «Module Manager» в `ARCHITECTURE.md`. Новых зависимостей нет.

### Что сделано
- `contract.rs`:
  - `ModuleId` с проверкой формата `domain.name`;
  - `ModuleDescriptor`;
  - `ModuleStatus { enabled, state }`;
  - `ModuleState`, `FailurePhase`, `BlockReason`;
  - `ModuleError`.
  - `Module`, `ModuleFactory` и `Health` не определены — это #9.
- `graph.rs`: проверка каталога (повторяющиеся ID, неизвестная зависимость, зависимость от себя, цикл с путём), детерминированный топологический порядок запуска и строго обратный порядок остановки, транзитивные зависимости и зависимые.
- `plan.rs`:
  - `enable` / `disable` / `recover` / `restart` → `ChangePlan { action, target, affected, steps, requires_confirmation, blockers }`;
  - `verify` → `Approved` / `NotApplicable` / `ConfirmationRequired` / `ImpactChanged`;
  - `expected_statuses` — итоговые статусы при успешном выполнении плана.

### Уточнения в рамках #7
- `recover` запускает заблокированных зависимых, у которых `by` входит в восстанавливаемые **этим планом** модули: цель и включаемые ею зависимости. Для основного случая (упала сама цель) это ровно формулировка #7. Расширение нужно, потому что `by` — первопричина: при `recover` модуля, заблокированного выключенной зависимостью X, его зависимые с `Blocked { by: X }` тоже разблокируются. Подтверждение обязательно, автоматики нет.
- Зависимость в переходном состоянии (`Initializing`, `Starting`, `Stopping`) блокирует план так же, как `Failed`/`Blocked`.
- `recover` модуля с `enabled = false` (отключение, при котором остановка не удалась: `Failed { phase: Stop }`) включает его заново.
- У неприменимого плана `steps` и `affected` пусты, чтобы его нельзя было выполнить по ошибке. `verify` проверяет в порядке: `NotApplicable` → `ConfirmationRequired` → `ImpactChanged` → `Approved`.
- Действие, неприменимое к текущему статусу цели (например, `enable` включённого модуля), — ошибка `ActionNotApplicable`, а не план.

### Временное разрешение неиспользуемого кода
`#[cfg_attr(not(test), allow(dead_code))]` на `mod modules;` с `TODO(#11)` — по согласованному плану (решение 22 в #13): у кода пока нет потребителей вне тестов. В тестовой сборке разрешение не действует, поэтому все варианты и методы покрыты тестами. Снимается в #11.

## 2026-11-09 — Issue #6: ядро — модель ошибок, логирование, состояние приложения

### Решения (согласованы пользователем)
- **Fallback логирования.** Если файловый лог недоступен, приложение пишет только в stdout с предупреждением и продолжает работать. Сбой файлового логирования не останавливает приложение; `setup` никогда не возвращает ошибку (иначе Tauri паникует).
- **Ротация.** Новый файл раз в сутки, хранятся последние **7** файлов (`MAX_LOG_FILES`, включая текущий); старые удаляются автоматически.
  - Удаление выполняет `tracing-appender` 0.2.5: при создании appender'а (старт приложения) и при каждой смене дня. Удаляются только обычные файлы с префиксом `atlas` и суффиксом `log`, самые старые по времени создания.
  - Это не только заявлено: тест `rolling_appender_keeps_at_most_max_log_files` (10 старых файлов → ровно 7, посторонние файлы не тронуты) **падает**, если убрать `.max_log_files(...)` (проверено мутацией: `left: 11, right: 7`).
- **Путь к логам на Windows:** `%LOCALAPPDATA%\com.inlerno.atlas\logs\atlas.YYYY-MM-DD.log`. Дата в имени и момент ротации — по **UTC** (`tracing-appender`), для Калининграда это 02:00.
- **Сброс буфера при выходе.** `tauri::App::run` завершает процесс через `std::process::exit`, деструкторы управляемого состояния не вызываются. Поэтому guard логов хранится в `AppState` и явно сбрасывается в `flush_logs()` на `RunEvent::Exit`. `flush_logs()` идемпотентен, переживает отравленный мьютекс и одновременные вызовы.
- **Фильтр уровня:** `RUST_LOG`, иначе `info`. Значение передаётся в чистую функцию; тесты не меняют окружение процесса (`std::env::set_var` — `unsafe` в Rust 2024).
- Сообщения крейта `log` (в том числе от Tauri) перенаправляются в `tracing` (feature `tracing-log`).
- Panic hook пишет панику в лог (`target: panic`) и вызывает предыдущий hook — стандартное поведение сохраняется.

| `thiserror` (`std`) | 2.0.21 | MIT OR Apache-2.0 |
| `tracing` (`std`, `default-features = false`) | 0.1.44 | MIT |
| `tracing-subscriber` (`std`, `registry`, `fmt`, `ansi`, `env-filter`, `tracing-log`) | 0.3.23 | MIT |
| `tracing-appender` | 0.2.5 | MIT |

Новые транзитивные пакеты в `Cargo.lock` (только добавления, версии существующих не менялись): `lazy_static` 1.5.1, `matchers` 0.2.0, `nu-ansi-term` 0.50.3, `sharded-slab` 0.1.7, `symlink` 0.1.0, `thread_local` 1.1.10, `tracing-log` 0.2.0, `valuable` 0.1.1 — все MIT или MIT/Apache-2.0.

- `valuable` 0.1.1 есть в `Cargo.lock`, но **не компилируется** ни для одной целевой платформы. Это опциональная зависимость `tracing-core`, которая включается только флагом `--cfg tracing_unstable`, а lockfile перечисляет все такие варианты. ### Ограничения
- При принудительном завершении процесса (`taskkill /F`, сбой нативного кода) последние буферизованные записи могут потеряться — `RunEvent::Exit` не наступает. Окно потерь мало: рабочий поток пишет непрерывно (эксперимент: очередь в 50 000 строк сброшена за 7,6 мс).
- Сообщения, появившиеся до `setup`, в файл не попадают.
- **Fallback не виден в Windows Release.** Release-сборка использует `windows_subsystem = "windows"`, консоли нет. Поэтому в режиме fallback (только stdout) предупреждение и сами логи пользователю не видны. Показ состояния логирования в UI — задача будущей диагностики.
- **Новый файл не удалось создать после смены дня.** `tracing-appender` пишет `Couldn't create writer for logs` в stderr и продолжает писать в прежний файл; приложение не падает. Если папку логов удалили во время работы, она создаётся заново при следующем открытии файла. Старые файлы удаляются до создания нового, поэтому лимит 7 сохраняется.
- **Паника внутри форматирования лог-сообщения.** Например, паника в `Debug`-реализации значения, переданного в событие. Взаимоблокировки нет: `tracing-core` при повторном входе направляет вложенное событие в пустой диспетчер. Но наш panic hook такую панику в лог **не** записывает — её выводит в stderr предыдущий (стандартный) hook. Проверено экспериментом.
- **Сбой моста `log` → `tracing`.** `try_init()` сначала ставит глобальный подписчик, затем `LogTracer`. Если до `setup` уже установлен другой `log`-логгер, `init` вернёт ошибку уже после установки подписчика: guard файлового лога удалится, и запись в файл молча прекратится (stdout продолжит работать). В ATLAS такого логгера нет (`tauri-plugin-log` не используется), поэтому случай сейчас недостижим. Решение пользователя: в коде не исправлять, только задокументировать.
- Записи после `flush_logs()` и сверх буфера в 128 000 строк отбрасываются без паники (режим `lossy` неблокирующего writer'а). Сброс при выходе ограничен ≈1,1 с (таймауты `WorkerGuard::drop`), поэтому выход не зависает.
