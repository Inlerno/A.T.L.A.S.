## ADR-011 Core-сервисы и optional-модули (2026-11-09, issue #7)
- **Контекст.** `ARCHITECTURE.md` перечислял Settings/Storage/Security рядом с Voice/Telegram, а жизненный цикл был описан только для optional-модулей. Не было сказано, загружаются ли модули динамически.
- **Решение.**
  - Core-сервисы — шина событий, Module Manager, хранилище настроек, логирование, хранилище, безопасность, диагностика — создаются при старте приложения и **не отключаются**.
  - Module Manager управляет только optional-модулями: AI provider, Voice, Memory, Telegram, Windows tools.
  - Модули — **compile-time Rust-код** в одном бинаре. Динамическая загрузка (DLL, плагины) не поддерживается.
- **Последствия.** Каталог модулей известен при сборке, граф зависимостей проверяется до запуска. Новый модуль требует новой сборки. Поверхность атаки и ABI-проблемы динамической загрузки исключены.
- **Статус:** принято.

## ADR-012 Двухфазные изменения состава модулей (2026-11-09, issue #7)
- **Контекст.** Отключение модуля может затронуть зависимые модули; пользователь должен видеть последствия и подтверждать их. Подтверждение нельзя доверять только UI, а состояние может измениться между показом и подтверждением. Сбои не должны вызывать автоматических перезапусков.
- **Решение.**
  - **Статус модуля** = `enabled` (решение пользователя) + `state` (фактическое состояние: `Stopped`, `Initializing`, `Starting`, `Running`, `Stopping`, `Failed { phase, error, at }`, `Blocked { by, reason }`). `by` — модуль-первопричина.
  - **Две фазы.** План (`enable` / `disable` / `recover` / `restart`) строится по графу и снимку статусов без побочных эффектов и показывает затронутые модули (`affected`) и блокирующие (`blockers`). `apply` пересчитывает план и выполняет его только если проверка в Rust (`verify`) одобрила подтверждение `{ confirmed, acknowledged }`. Иначе — `ConfirmationRequired`, `ImpactChanged` (с новым планом) или `NotApplicable`; это ожидаемые исходы, а не ошибки.
  - **Подтверждение** нужно, если `affected` не пуст. **`recover` подтверждается всегда**, даже без затронутых модулей.
  - **`enable`** включает и запускает выключенные транзитивные зависимости (Q2). Зависимость в `Failed`, `Blocked` или в переходном состоянии блокирует план.
  - **`disable`** отключает и останавливает включённые транзитивно зависимые в обратном порядке зависимостей. Итог: `enabled = false`, `Stopped`. Пользовательское отключение **не** даёт `Blocked`.
  - **Сбой во время работы** (#9): работающие транзитивно зависимые останавливаются в обратном порядке и переходят в `Blocked { by, DependencyFailed }`, оставаясь `enabled = true` (Q1).
  - **Включённый модуль с выключенной зависимостью** (загрузка конфигурации, #10) → `Blocked { by, DependencyDisabled }`.
  - **Неизвестное решение пользователя** (#10, ADR-015). `enabled: Option<bool>`: `None` — конфигурация ещё не загружена (только до готовности менеджера) или её запись не прочитана (`ConfigUnavailable`). Решение не угадывается:
    - к модулю с `None` не применимо ни одно действие (`ActionNotApplicable`);
    - для `enable` и `recover` такая зависимость — блокирующая (`blockers`), её никто не включает неявно;
    - каскады `disable` и `restart` берут только `Some(true)`: модуль с `None` в план не попадает и не записывается;
    - зависимый, включённый пользователем, при запуске получает `Blocked { by, DependencyConfigUnavailable }`.
  - **Запись решений** (#10, ADR-015): шаги `Enable` / `Disable` подтверждённого плана записываются в хранилище одним атомарным пакетом **до** выполнения; ошибка записи — ничего не меняется. План, который запустил бы модуль с некорректными настройками, отклоняется до записи (`InvalidSettings`).
  - **`recover`** (из `Failed` или `Blocked`) включает и запускает недостающие зависимости цели, запускает цель новым экземпляром и затем — транзитивно зависимые в `Blocked`, у которых `by` входит в восстанавливаемые этим планом модули и все зависимости будут работать.
  - **`restart`** (только `Running`): работающие зависимые останавливаются в обратном порядке и запускаются снова после цели.
  - **Никаких автоматических переходов**: восстановление или включение зависимости не запускает заблокированные модули само; выход из `Failed`/`Blocked` — только подтверждённый `recover`.
  - Изменения статусов публикуются **только через центральную типизированную шину событий** (#8, ADR-013); других механизмов уведомлений нет.
- **Последствия.** Устаревшее подтверждение отклоняется (`ImpactChanged`). Логика планов — чистые функции с юнит-тестами (`src-tauri/src/modules/plan.rs`), применение — в #9.
- **Статус:** принято.

## ADR-013 Центральная типизированная шина событий (2026-11-09, issue #8)
- **Контекст.** Ядру, модулям и (позже) UI нужно узнавать об изменениях — прежде всего статусов модулей — без прямых связей между компонентами. Несколько механизмов уведомлений сделали бы порядок и источник событий непредсказуемыми, а логика в канале доставки стала бы скрытой автоматикой, которую запрещает ADR-012.
- **Решение.**
  - **Одна центральная шина** — `EventBus` (`src-tauri/src/events/`) поверх `tokio::sync::broadcast`. Создаётся в `setup`, хранится в `AppState`. Это **единственный механизм межмодульных уведомлений**: прямые callback-вызовы, Observer, отдельные каналы и обход шины запрещены (решение 24 в #13).
  - **Только доставка уведомлений.** Запросы, ответы и команды через шину не передаются. Шина не изменяет статусы модулей, не инициирует `enable` / `disable` / `recover` / `restart`, не запускает автоматическое восстановление, не создаёт фоновых задач и не имеет доступа к менеджеру и модулям — она знает только типы событий (решение 25).
  - **Строгая типизация.** `EventEnvelope { seq, at_unix_ms, source, event }`, где `event: AppEvent` — enum по доменам. Сейчас единственное событие — `AppEvent::Module(ModuleEvent::StatusChanged { id, previous, current })`. Новые варианты добавляются вместе с кодом, который их отправляет: `HealthChanged` — #9, `SettingsChanged` — #10, демо-событие — #12. События не содержат секретов.
  - **Источник проставляет ядро.** `publish(event)` не принимает источник и всегда ставит `EventSource::Core`. Модули в #9 только подписываются. Публикация модулями — впервые в #12; тогда же появится `EventSource::Module(ModuleId)`, который проставляет ядро.
  - **Порядок.** `publish`, `subscribe` и `close` выполняются под одной блокировкой шины и не перемежаются. `publish` присваивает `seq` (1, 2, 3, …) и ставит событие в очередь под этой блокировкой. Поэтому все подписчики получают события в порядке `seq`, в том числе при одновременной публикации из нескольких потоков; события одного потока сохраняют его порядок. `at_unix_ms` — справочное время, порядок задаёт только `seq`.
  - **Без истории.** Подписчик получает только события, опубликованные после подписки. Чтобы следить за статусами, нужно сначала подписаться, затем прочитать снимок (#9).
  - **Переполнение.** Буфер — `capacity` событий на подписчика, по умолчанию 256. Допустима только степень двойки до 4096: `tokio` округляет ёмкость вверх до степени двойки, и так заданное значение точно совпадает с порогом `Lagged`. Ёмкость задаётся в коде, а не пользователем; неверное значение — паника при создании, для значения по умолчанию это проверяется при компиляции. `publish` никогда не ждёт. Подписчик, отставший больше чем на `capacity`, получает `Lagged { missed }` с точным числом потерянных событий, затем — самое старое из сохранённых; он обязан пересинхронизироваться по снимку. Отправители и остальные подписчики не затрагиваются.
  - **Без подписчиков** публикация — не ошибка: событие никому не доставляется и не сохраняется, `seq` растёт.
  - **Закрытие.** `close()` на `RunEvent::Exit` или удаление всех handle: подписчики получают все события, опубликованные до закрытия, затем `Closed`. После закрытия `publish` возвращает `BusClosed`, а новый подписчик сразу получает `Closed`. `close()` идемпотентен и действует на все клоны.
  - **Требование к использованию API.** Waker задачи, которая ждёт `Subscriber::recv`, не должен синхронно вызывать шину (`publish`, `subscribe`, `close`): подписчики пробуждаются, пока блокировка шины удерживается, и такой вызов приведёт к взаимоблокировке. Waker'ы `tokio` и других распространённых executor'ов только ставят задачу в очередь и требование выполняют.
  - **Разграничение механизмов** (решение 26 в #13, реализуется в #9): `mpsc` — передача команд менеджеру; `oneshot` — получение результата выполнения команды; `watch` — только чтение актуального снимка статусов, подписка через `changed()` запрещена; Event Bus — единственный механизм уведомления об изменениях, статусы — через `StatusChanged`.
- **Уточнения исходного текста #8** (приняты пользователем 2026-11-09 по ревью PR #17, решение 27 в #13):
  1. **`EventSource::Module(ModuleId)` добавляется в #12** вместе с первой реальной публикацией модульных событий. Без отправителя вариант нигде не создаётся, а искусственный тест или точечный `allow` ради него не нужны.
  2. **Тестовые макросы `tokio` (`macros`) не подключаются:** зависимости не добавляются только ради удобства тестов. Тесты запускают futures через `tokio::runtime::Builder::new_current_thread()` (feature `rt`).
  3. **Явный `close()` на выходе** необходим: `App::run` завершает процесс через `std::process::exit`, поэтому handle шины в `AppState` никогда не удаляется и без явного закрытия подписчики не получили бы `Closed`.
  4. **Ёмкость — степень двойки до 4096:** порог переполнения точно равен заданному значению, без скрытого округления.
- **Проверка.** Порядок при одновременных вызовах проверяется детерминированно: тест останавливает публикующий поток в критической точке (у события уже есть `seq`, но оно ещё не отправлено) и проверяет, что `publish`, `close` и `subscribe` из других потоков ждут блокировку, а все подписчики получают события в порядке `seq`. Точки перехвата есть только в тестовой сборке (`#[cfg(test)]`), в приложении их нет. Стресс-тесты со случайным чередованием потоков — дополнительная проверка.
- **Последствия.** Порядок и источник событий предсказуемы и проверяются тестами. Медленный подписчик не тормозит ядро, но может потерять события — их восполняет пересинхронизация по снимку. Мост в UI (#11) получает события как обычный подписчик шины.
- **Статус:** принято; уточнения согласованы пользователем 2026-11-09.

## ADR-014 Жизненный цикл модулей и политика сбоев (2026-11-09, issue #9)
- **Контекст.** Планы из ADR-012 нужно выполнять: создавать экземпляры модулей, вызывать их методы и переживать сбои. Модуль может вернуть ошибку, запаниковать или зависнуть, а приложение должно продолжать работать. При этом статусы, события и фактический жизненный цикл должны совпадать, а автоматического восстановления быть не должно.
- **Решение.**
  - **Менеджер — actor** (`src-tauri/src/modules/manager.rs`). Одна задача владеет реестром и выполняет команды строго по очереди. Это единственный компонент, меняющий статусы; инвариант (решение 23) проверяется при каждом переходе. Каждое изменение сначала попадает в реестр и снимок, затем публикуется на шине.
  - **Механизмы** (решение 26):
    - `mpsc` — команды менеджеру. Сюда же надзор присылает отчёты о сбое фоновой задачи и о завершении проверки health; модулю отправитель не доступен;
    - `oneshot` — результат каждой команды;
    - `watch` — снимок статусов только для чтения, `changed()` не используется;
    - уведомления — только `StatusChanged` и `HealthChanged` на центральной шине.
  - **Контракт** (`contract.rs`): `ModuleFactory` (`descriptor`, `create`) и `Module` (`initialize`, `start`, `stop`, `health_check`). Асинхронные методы возвращают `Pin<Box<dyn Future + Send>>`, крейт `async-trait` не нужен. Экземпляр создаётся фабрикой при каждом запуске (`enable`, `recover`, `restart`) и удаляется после остановки или сбоя; состояние после паники не используется повторно.
  - **Контекст** (`context.rs`): подписка на шину, токен отмены и фоновые задачи под надзором (`TaskTracker` + `CancellationToken`). Доступа к менеджеру и публикации событий у модуля нет.
  - **Изоляция.** Каждый вызов модуля выполняется в отдельной задаче tokio с таймаутом: паника остаётся в этой задаче, зависание не останавливает менеджер. Экземпляр тоже удаляется вне задачи менеджера — на пуле блокирующих потоков (`tokio::task::spawn_blocking`), и ожидание удаления ограничено: паника или зависание `Drop` не останавливают менеджер (исправление D1, 2026-11-10). Запущенную задачу `spawn_blocking` прервать нельзя: по истечении срока менеджер только перестаёт её ждать.

    | Таймаут | Значение | Почему |
    |---|---|---|
    | `initialize` | 30 с | модуль может проверять локальные движки или подключения; тяжёлая загрузка — в фоновых задачах |
    | `start` | 10 с | запуск только начинает работу |
    | `stop` | 5 с | отключённый модуль должен останавливаться быстро |
    | фоновые задачи после отмены | 2 с | затем оставшиеся прерываются |
    | `health_check` | 5 с | проверку запрашивает пользователь и ждёт ответа |
    | общий таймаут выхода | 10 с | ограничивает время, на которое зависший модуль может задержать закрытие |

    Срок `stop` общий для `stop` и удаления экземпляра: удаление получает остаток тех же 5 с. После неудачных `initialize` / `start` удаление ждётся до 5 с. Таблица сроков от этого не меняется.

  - **Сбои.**
    - `initialize` или `start`: ошибка, паника или таймаут → `Failed { phase }`. `stop` не вызывается: экземпляр не запускался. Порядок — решение 7: `Failed { phase }` → отмена токена → удаление экземпляра → ожидание фоновых задач → прерывание оставшихся. Зависший `Drop` не задерживает `Failed`; неудачное удаление пишется в журнал, а статус хранит фазу и ошибку модуля. После паники, таймаута или прерывания экземпляр удаляется в задаче вызова (раскруткой паники или tokio), менеджер его не ждёт.
    - **Ресурсы экземпляра** (уточнение пользователя к решению 6). При ошибке `initialize` или `start` модуль сам освобождает уже выделенные ресурсы и только затем возвращает ошибку. Удаление экземпляра (`Drop`) не должно оставлять ресурсов: после паники или таймаута `Drop` — единственный код модуля, который ещё выполняется. Экземпляр владеет всем, что выделил (файлы, сокеты, устройства, нативные дескрипторы, потоки, дочерние процессы). Менеджер сам освобождает только фоновые задачи, запущенные через контекст. Правило записано в контракте `Module` (`contract.rs`).
    - Фоновая задача: ошибка или паника → сразу `Failed { phase: Run }`. Затем экземпляр останавливается (`stop`, удаление, ожидание задач, прерывание оставшихся). Затем работающие транзитивно зависимые останавливаются в обратном порядке зависимостей и получают `Blocked { by, DependencyFailed }`. Если их собственная остановка не удалась — `Failed { phase: Stop }`.
      - **После запроса выхода** (исправление D2) отчёт о сбое только пишется в журнал: `warn` — экземпляр работал на момент выхода, `debug` — уже был остановлен; текст ошибки сохраняется в обоих случаях. Статус не меняется, остановки и каскада нет: модуль останавливает `shutdown_all`, и итог определяет результат этой остановки (`stop` успешен → `Stopped`). Отчёт, обработка которого уже началась до запроса выхода, доводится до конца в пределах общего срока.
    - Остановка: отмена токена → `stop` → удаление экземпляра → ожидание фоновых задач → прерывание оставшихся. Ошибка, паника или таймаут `stop`, паника или превышение срока удаления, прерванные задачи → `Failed { phase: Stop }`; при `disable` итог `enabled = false`. Сбой остановки одного модуля не прерывает остановку остальных.
      - Тексты прежние: «Модуль аварийно завершился», «Модуль не ответил вовремя». Причину различает журнал: сообщение и поле `call` (`stop` или `drop`). В статусе остаётся первая ошибка: `stop`, затем удаление, затем прерванные задачи; остальные пишутся в журнал.
    - Сбой посреди плана: упавший модуль → `Failed` и в этом плане больше не запускается. Модули плана, зависящие от него, → `Blocked { by }`, где `by` — первопричина. Независимые модули продолжают работать.
    - Отчёт о сбое от экземпляра, который уже остановлен (например, после `restart`), игнорируется: отчёты несут номер экземпляра.
  - **Health — только по запросу.** Результат информационный и не меняет состояние. `HealthChanged` публикуется, когда значение отличается от предыдущего для того же экземпляра.
    - Таймаут → `Unhealthy("проверка не ответила")` без смены состояния. Не ответившая проверка продолжает держать экземпляр, новая не запускается.
    - Поздний ответ возвращает экземпляр. Поздняя паника → `Failed { phase: HealthCheck }` с каскадом.
    - При остановке менеджер ждёт такую проверку в пределах таймаута `stop`. Если она так и не ответила, модуль останавливается без вызова `stop` и получает `Failed { phase: Stop }`.
    - Паника проверки → `Failed { phase: HealthCheck }` с каскадом.
  - **Без автоматики.** Ни сбой, ни прошедшее время, ни восстановление зависимости, ни результат health не запускают модули. Модули запускаются только подтверждёнными `enable`, `recover` и `restart`.
  - **Выход из приложения** (решение 28). Первый запрос выхода откладывается (`prevent_exit`). Модули останавливаются вне главного потока, затем выход запрашивается снова и проходит — цикла нет. На `RunEvent::Exit` вызываются `close_events()`, затем `flush_logs()`. Если выход произошёл без завершённой остановки (например, при `restart`, где отложить выход нельзя), модули останавливаются в `Exit` с тем же общим таймаутом; фоновая остановка тогда выход повторно не запрашивает.
  - **Истечение общего таймаута** (требование пользователя к MM-4):
    - *Как прекращается работа.* После запроса выхода новые запуски не начинаются, а оставшиеся шаги текущего плана пропускаются. Идущие `initialize`, `start` и `health_check` прерываются сразу (`Failed { phase }` с текстом «Операция прервана завершением приложения»). Остановки ограничены сроком. Модули, до которых к сроку не дошла очередь, завершаются принудительно без `stop`: токен отменяется, удаление экземпляра запускается вне задачи менеджера и не ждётся, фоновые задачи прерываются. Процесс завершается сразу после этого.
    - *Как фиксируется ошибка.* Статус `Failed { phase: Stop }` с текстом «Модуль не успел остановиться при завершении приложения», событие `StatusChanged`, запись `error` в логе (модуль и число прерванных задач) и запись в `StopReport.failed`. `enabled` не меняется. Удаления экземпляров, которые менеджер перестал ждать и которые к концу `shutdown_all` ещё не завершились, перечисляются в журнале (`warn`) до ответа на команду выхода; успевшие завершиться к этому моменту не перечисляются.
    - *Как гарантируется отсутствие публикаций после закрытия шины.* Команда выхода публикует все изменения статусов в `shutdown_all`, до ответа. Затем (исправления D2, L1; порядок — вариант B, 2026-11-10):
      1. менеджер разбирает очередь, не закрывая её;
      2. пишет `module manager stopped`;
      3. закрывает очередь;
      4. разбирает то, что пришло между шагами 1 и 3;
      5. отпускает повторные запросы выхода — они получают `ShutDown`;
      6. отвечает на команду выхода.

      При разборе ничего не выполняется: отчёты о сбоях только пишутся в журнал (`warn` или `debug`, как выше), статусы не меняются; команды получают `ShutDown`; завершение не ответившей проверки health ничего не делает; повторный запрос выхода ждёт шага 5. Запрос, отправленный после закрытия очереди, сразу получает `ShutDown` — уже после строки о завершении. Поэтому вызывающий (например, запасной путь `RunEvent::Exit` при `restart`) не может сбросить журнал раньше этой строки. После ответа менеджер ничего не пишет в журнал, не публикует и не выполняет. Отчёт, который уже нельзя отправить менеджеру, супервизор фоновой задачи пишет в журнал сам (`warn`). `close_events()` вызывается только после ответа. Кроме того, сама шина отклоняет публикации после закрытия.

      *Остаточное ограничение.* Отчёт о сбое, пришедший около момента закрытия очереди (между шагами 1 и 3), пишется на шаге 4 — после `module manager stopped`, но до ответа. Если в этот момент запасной путь выхода уже получил `ShutDown` на запрос, отправленный после закрытия, такая строка может оказаться после `flush_logs()` и потеряться.
  - **`panic = "abort"` запрещён** и проверяется в CI: изоляция держится на раскрутке стека (unwind).
- **Принятые решения** (пользователь, 2026-11-09, ревью PR #20; решение 29 в #13). Приняты 12 решений, которых не было в тексте #9:
  1. ручные boxed futures вместо `async-trait`;
  2. без `macros` у tokio — отмена через `CancellationToken`;
  3. `Module: Send + Sync`;
  4. поведение при проверке health без ответа;
  5. `HealthChanged` только при изменении результата;
  6. `stop` не вызывается после неудачных `initialize` / `start`;
  7. `Failed` сразу, освобождение ресурсов после;
  8. выход прерывает текущие операции;
  9. двухфазный выход через `ExitRequested` / `Exit`;
  10. сообщения для пользователя по-русски;
  11. некорректный каталог — запуск без модулей;
  12. таймауты из таблицы выше.

  Два уточнения пользователя:
  - **к решению 6** — обязанность модуля освобождать частично выделенные ресурсы (см. «Ресурсы экземпляра» выше);
  - **к решению 11** — ошибка каталога обязательно пишется в лог на уровне `error` вместе с причиной; молчаливого игнорирования неисправной регистрации нет. Это проверяет тест `an_invalid_catalog_is_logged_and_leaves_the_manager_without_modules`.
- **Ограничения таймаутов.** Таймаут — обычный асинхронный: он прерывает вызов только там, где тот уступает управление (`.await`).
  - **Блокирующий код** (например, блокирующий нативный вызов) таймаутом не прерывается. Такой код занимает поток runtime, пока не вернётся. Менеджер при этом продолжает работу: вызов идёт в отдельной задаче. При выходе поток завершается вместе с процессом.
  - **Блокирующую работу модуль выносит в отдельный поток** (например, `tokio::task::spawn_blocking`), чтобы его асинхронные методы продолжали уступать управление.
  - **Падения нативного кода**, убивающие процесс, тоже не перехватываются.
  - **Удаление экземпляра** срок не прерывает. Зависший `Drop` занимает поток пула, пока не вернётся или пока процесс не завершится (`std::process::exit`, где незавершённый `Drop` обрывается). Освобождение ресурсов экземпляра к ответу на команду выхода не гарантируется. Поздний итог удаления не меняет опубликованный статус. Двойная паника (вызова и `Drop` при раскрутке) скорее всего завершает процесс.
  - **Автозапуска модулей при старте пока нет** — это #10.
- **Последствия.** Статус всегда соответствует фактическому жизненному циклу экземпляра и проверяется тестами после каждого перехода. Сбой одного модуля затрагивает только его зависимых. Выход ограничен по времени и при зависших модулях.
- **Статус:** принято пользователем 2026-11-09 (архитектура, 12 дополнительных решений с двумя уточнениями, зависимости). Исправления D1 (удаление экземпляра вне задачи менеджера), D2 (сбои фоновых задач после запроса выхода) и L1 (строка `module manager stopped` до ответа) — по решению пользователя 2026-11-10, до слияния. Слияние PR #20 — после ручной проверки на Windows.

## ADR-015 Конфигурация модулей, настройки и автозапуск (2026-11-12, issue #10, MM-5A)
- **Контекст.** До #10 все модули при старте были выключены, а у модулей не было собственных настроек. Нужно: хранить решение пользователя (`enabled`) и настройки модуля, проверять настройки, запускать при старте модули, оставленные включёнными, и не угадывать решение, если конфигурацию прочитать не удалось. MM-5 разделён (решения пользователя, #13): MM-5A (#10) — контракты и жизненный цикл с хранилищем в памяти; MM-5B (#21) — хранение в SQLite, сохранение между запусками и восстановление недоступной конфигурации (`replace_config`).
- **Решение.**
  - **Конфигурация** (`src-tauri/src/modules/config.rs`): запись `ModuleConfig { enabled, settings }`; асинхронный трейт `ModuleConfigStore` с `load(id)` и `save_batch(записи)` — пакет сохраняется атомарно, все записи или ни одной, в том числе при отмене. `InMemoryConfigStore` — одна блокировка на пакет, клоны разделяют данные. Конфигурацией владеет менеджер: читает хранилище один раз при старте, дальше только пишет — одним пакетом на команду. Записи модулей, которых нет в каталоге, не читаются и не меняются.
  - **Настройки.** Методы фабрики `default_settings()` (по умолчанию `{}`) и `validate_settings(&Value) -> Result<(), ModuleFailure>` (по умолчанию принимается только `{}`): проверять нужно и выключенный модуль, у которого нет экземпляра. Методы чистые и быстрые. Общие проверки до валидатора модуля: глубина вложенности ≤ 128 (итеративно), корень — объект, компактный JSON ≤ 65 536 байт (считается без построения строки), ключи, похожие на секреты (`password`, `token`, `api-key`, `bot_token` и т. п., на любой глубине; `token_ref`, `max_tokens` проходят) — это страховка, не гарантия. Ошибка → `ModuleError::InvalidSettings { module, reason }`; в причине путь, но не значение. Настройки передаются экземпляру через `ModuleContext::settings()` — доступны с `initialize`, одинаковы на всю жизнь экземпляра. Трейт `Module` не меняется.
  - **Изоляция фабрики.** `create`, `default_settings` и `validate_settings` вызываются под `catch_unwind` (работает, потому что `panic = "abort"` запрещён, ADR-014): паника `create` → `Failed { Initialize, «Модуль аварийно завершился» }`; паника `default_settings` → значения по умолчанию некорректны; паника валидатора → настройки отклонены. Подробности — только в журнале.
  - **Неизвестное решение** (уточняет ADR-012 и решение 23). `ModuleStatus.enabled: Option<bool>`, новое состояние `ConfigUnavailable { error, at }`, фаза `FailurePhase::Settings`, причина `BlockReason::DependencyConfigUnavailable`. Инвариант: активные и `Blocked` — только `Some(true)`; `ConfigUnavailable` — только `None`; `None` — только с `ConfigUnavailable` или со `Stopped` до готовности.
  - **Загрузка** — по модулям в порядке запуска, каждое чтение ожидается до запроса выхода:
    - запись есть → `{ Some(enabled), Stopped }` и её настройки;
    - записи нет → `default_enabled` и `default_settings()`; при загрузке ничего не записывается;
    - ошибка чтения → `{ None, ConfigUnavailable { «Не удалось прочитать конфигурацию модуля» } }`: значения по умолчанию не подставляются, запись не перезаписывается, подробности хранилища — только в журнале. К модулю не применимо ни одно действие, `get_settings` / `update_settings` → `ConfigUnavailable`. **Внутри сеанса выхода из этого состояния нет**; при следующем запуске запись читается снова. Восстановление (`replace_config`) — MM-5B;
    - чтение, прерванное выходом, — не ошибка чтения: модуль остаётся `{ None, Stopped }`;
    - на каждый модуль публикуется ровно один `StatusChanged` с `previous = { None, Stopped }`; `SettingsChanged` при загрузке нет.
  - **Некорректные настройки** (сохранённые или по умолчанию): у включённого модуля при запуске → `Failed { Settings, «Настройки модуля некорректны: …» }`, экземпляр не создаётся; у выключенного — только запись в журнал, `Failed` у выключенного модуля не бывает. В снимке — `valid = false`.
  - **Автозапуск** — включённые модули в топологическом порядке. Для каждого берётся первая проблемная транзитивная зависимость в порядке запуска: выключена → `Blocked { by, DependencyDisabled }`; конфигурация недоступна → `Blocked { by, DependencyConfigUnavailable }`; `Failed` → `Blocked { by, DependencyFailed }`. Неявных включений, повторных попыток и автоматического восстановления нет; выход из `Failed` / `Blocked` — только подтверждённый `recover`. `Failed` и `Blocked` — состояния только текущего запуска: при следующем запуске включённые модули стартуют обычным порядком, и это не считается автоматическим восстановлением.
  - **Снимок и готовность.** `watch` хранит `ModulesSnapshot { ready, statuses, settings, restart_required }` только для чтения (решение 26). Контракт готовности:
    1. `ready = true` означает, что первоначальная загрузка конфигурации завершена и снимок статусов достоверен.
    2. `ready` выставляется один раз — когда подготовка закончилась: загрузка завершена, а автозапуск завершён, пропущен или прерван выходом. Обратно в `false` не возвращается.
    3. Пока `ready = false`, `statuses()`, `plan()` и `get_settings()` возвращают `NotReady`. После — читают снимок, в том числе во время и после выхода.
    4. `ready = true` не гарантирует, что менеджер продолжает принимать обычные команды: после запроса выхода они не выполняются (`ShutDown`), даже если `ready = true`.
    5. `ManagerReady` публикуется один раз, сразу после установки `ready`. Он означает завершение подготовки достоверного начального снимка, а не гарантию продолжения нормальной работы приложения.
    6. Выход во время автозапуска: текущая операция автозапуска завершается или прерывается — прерванный модуль получает `Failed { Initialize }` или `Failed { Start }` с текстом «Операция прервана завершением приложения» (ADR-014), — затем `ready = true` и `ManagerReady` — до событий `shutdown_all` и до ответа на `Shutdown`. Включённые модули, до которых автозапуск не дошёл, сохраняют `{ Some(true), Stopped }`.
    7. Выход во время загрузки: загрузка прекращается, `ready` остаётся `false`, `ManagerReady` не публикуется.

    Команды, отправленные во время подготовки, ждут в очереди и выполняются после неё по порядку; отчёты о сбоях модулей, запущенных автозапуском, — тоже.
  - **Запись решений** — ADR-012: проверки → один `save_batch` (ожидание — до срока выхода) → только после успеха изменения в памяти и выполнение. Ошибка или срок → `ManagerError::Store`, ничего не меняется. `restart` и `recover` без шагов `Enable` ничего не пишут.
  - **`update_settings(id, value)`:** после запроса выхода → `ShutDown`; неизвестный модуль → `UnknownModule`; `ConfigUnavailable` → `ManagerError::ConfigUnavailable`; проверка; то же значение → ничего; запись одного модуля с текущим `enabled`; затем снимок и `SettingsChanged { id, restart_required }` без значений. Новые настройки применяются только к следующему экземпляру: у работающего модуля `restart_required = true`, применить их можно подтверждённым `restart`. **Автоматического перезапуска нет.** `restart_required` сбрасывается вместе с переходом из `Running` (остановка, сбой, замена экземпляра) и при возврате прежнего значения.
  - **Выход** (дополняет ADR-014 и решение 28; семантика прерывания ADR-014 не меняется):
    - сигнал выхода приоритетнее очереди команд: менеджер ждёт очередь под `requested`, а сообщение, полученное вместе с запросом, не выполняется;
    - режим выхода: текущая операция завершается по правилам ADR-014; затем накопленные сообщения разбираются без ожидания (команды — `ShutDown`, отчёты о сбоях — только журнал), затем `shutdown_all`, затем — как в ADR-014 (строка о завершении, закрытие очереди, ответ). В режиме выхода статусы меняет только `shutdown_all` (проверяется `debug_assert`);
    - обработка сбоя фоновой задачи, начатая до запроса выхода, прерывается на ближайшей безопасной точке — между остановками зависимых: идущая остановка доводится до конца, следующая не начинается, остальных зависимых останавливает `shutdown_all` (они получают `Stopped`, а не `Blocked`); в журнале — модуль и число переданных зависимых. То же — для паники проверки health;
    - запись в хранилище в идущей команде ждётся не дольше общего срока выхода.
  - **События** (новые варианты): `ModuleEvent::SettingsChanged { id, restart_required }` и `ModuleEvent::ManagerReady`. Порядок: загрузка — один `StatusChanged` на модуль; автозапуск — `StatusChanged` по переходам; конец подготовки — `ManagerReady`; `update_settings` — только `SettingsChanged`.
  - **Логи и секреты.** Значения настроек не попадают в журнал, события и `Debug` (`ModuleConfig`, `SettingsEntry`, `ModuleSettings` скрывают значения). Секреты в настройках запрещены: только ссылка на хранилище ОС (`token_ref`). Строки журнала для проверки на Windows: `module configuration loaded modules=… stored=… defaults=… unavailable=…`, `autostart finished started=… failed=… blocked=… interrupted=…`, `module manager ready`.
- **Последствия и ограничения.**
  - Хранилище в MM-5A — в памяти: решения и настройки не сохраняются между запусками приложения (сохранение — MM-5B, #21).
  - Путь `ConfigUnavailable` в работающем приложении до MM-5B недостижим (хранилище в памяти не отказывает); он проверяется тестами на хранилище с отказами.
  - Зависшее хранилище держит готовность до запроса выхода, а команду — до общего срока выхода; таймауты вызовов хранилища — вопрос MM-5B.
  - Методы фабрики выполняются в задаче менеджера синхронно и сроком не ограничены — по контракту они чистые и быстрые (то же ограничение, что для блокирующего кода в ADR-014).
  - Строка ADR-014 «Автозапуска модулей при старте пока нет — это #10» после MM-5A устарела; ADR-014 в PR #10 не менялся — правка ожидает решения пользователя.
